# Решение

## Затраченное время

Время разработки: 2,5 часа
Время настройки окружения: 1 час

## Найденные причины

### 1. Быстрое переключение -> данные предыдущей заявки

**Воспроизведение.** Редактор, `DEMO_LATENCY=1`. Клик по #101 (ответ 1.1 с), сразу #102 (0.1 с). 102 приходит раньше 101; карточка на миг показывает 102, потом подменяется на 101, хотя в списке выбрана 102. 

**Причина.** В `TicketPanel.jsx` загрузка по `selectedId` и `save()` безусловно писали в state. Устаревший ответ (медленный GET/POST) выигрывал гонку. API при этом отдавал корректные JSON по id.

**Исправление.** На загрузке: флаг `cancelled` + cleanup в `useEffect` — поздний ответ игнорируется. На save: запоминаем `savedId`, после ответа сверяемся с `selectedIdRef`, тикет и историю трогаем если всё ещё на этой заявке; список через `onChanged` — всегда (по id).

**Проверка.** Вручную 101 на 102 и обратно несколько раз — карточка не откатывается. Save на 102 → сразу клик 103 — карточка остаётся 103, строка 102 в списке при успехе обновляется. 101 может прийти позже — UI не реагирует. 

### 2. Карточка заявки без источника

**Воспроизведение.** Открыть #103 (в seed `source_id = NULL`). UI показывает ошибку 500. Список при этом живой.

**Причина.** `TicketRepository::find()` всегда собирал `'source' => array('id' => (int) $source['id'], ...)`.
При отсутствии строки в `sources` `pg_fetch_assoc` даёт `false`, обращение к полям -> 500 в `bootstrap.php`.
Контракт и React уже ждут `source: null`.

**Исправление.** Если source-row нет — отдаём `'source' => null`, иначе как раньше `{id, name}`.

**Проверка.** #103 — «Не указан». `tools/test_sol.py`: GET #103 -> 200, `source=null`.

### 3. Viewer / дыры в смене источника

**Воспроизведение.**
- UI кнопку прячет, но `POST /api/tickets/102/source` с cookie viewer + CSRF раньше менял источник (нет `FUNC_TICKETS_SOURCE_EDIT` на сервере).
- Редактор + архив #104 смена проходила.
- Повторный выбор того же source писал лишнюю строку в `ticket_history`.
- UPDATE и INSERT шли двумя отдельными запросами без транзакции.

**Причина.** В `routes.php` на POST был CSRF, но не право редактирования. В `changeSource` не было проверки `archived`, идемпотентности и `BEGIN/COMMIT`. Порядок заявка, архив, source не соблюдался (валидация source до проверки заявки).

**Исправление.**
- `routes.php`: после CSRF — `requirePermission(..., 'FUNC_TICKETS_SOURCE_EDIT')` (отказ до изменения данных).
- `changeSource`: 404 если нет заявки, 403 если `archived`, 400 если `source_id` не JSON-int > 0 или нет в `sources`, если source тот же — 200 без INSERT, иначе транзакция UPDATE + INSERT history; `employee_id` только из сессии.

**Проверка.** `tools/test_sol.py`: viewer 403 (данные не меняются; чужой `employee_id` в body не помогает), невалидный source 400, тот же - без новой history, смена + employee из сессии, 401 без логина.

## Решения и компромиссы

Для гонки хватило cancelled на загрузке и selectedIdRef на save — без AbortController и правок api.js.
Список после save обновляем всегда по id. Null source закрыли guard’ом в find, React не трогали. 
Право edit — в routes; порядок 404,архив, source, идемпотентность и транзакция — в репозитории.

Ручная проверка гонки UI: быстрый клик #101 на #102.


## Одновременное редактирование

Два редактора почти одновременно шлют разный `source_id`: оба пройдут проверки, оба закоммитят свои транзакции. 
Победит последний COMMIT — в `tickets` останется его source, в `ticket_history` будут две записи. 
Потери другого изменения как отдельной ошибки клиенту нет.

## Оставшиеся ограничения

- Concurrent edit двумя сотрудниками не защищён.
